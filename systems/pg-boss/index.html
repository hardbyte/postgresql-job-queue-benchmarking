What this system is built around

PostgreSQL job queues with configurable duplicate policies, retries, scheduling and transaction adapters.

A useful starting point

Consider when a Node application needs database transaction adapters plus queue policy controls. Choose heartbeat, expiration and worker transaction settings explicitly for your workload.

Editorial fit, based on the cited design. Verify against your workload.

Concise claims with their scope intact. “Not verified” means this review did not establish the answer.

Claiming & concurrency

Documented

localConcurrency is per process. Group concurrency options and queue policies have separate scopes; do not treat a per-process number as a fleet-wide limit.

Transactional enqueue

Documented

send, insert, fetch and complete accept a db transaction adapter. transactional workers can commit same-database handler SQL with completion. External API calls are outside that transaction.

ORM transaction adapters ↗ Worker concurrency and transactional handlers ↗

Crash recovery & retries

Documented

Heartbeat detection is disabled by default; expiration defaults to 15 minutes. Both route to retry/failure policy. Late settlement is guarded by the claimed retryCount.

Queue policies, retry and recovery ↗

Delayed & recurring work

Documented

Schedules need a running instance; evaluation has minute-level filing precision. Catch-up is skip by default, with a once policy for missed occurrences.

Uniqueness / deduplication

Documented

standard, short, singleton, stately, exclusive and key_strict_fifo policies have different queued/active constraints and can use singletonKey. These are not permanent external-effect deduplication.

Postgres extension required

Not required

Stock PostgreSQL is the primary backend; installation creates pg-boss schema objects. Current package requires Node >=22.12; overview lists PostgreSQL >=13.
