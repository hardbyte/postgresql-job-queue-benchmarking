What this system is built around

A Postgres-backed ActiveJob backend for Rails with threads, scheduling, an integrated dashboard and concurrency extensions. Default job claims use advisory locks; current main also documents an experimental SKIP LOCKED mode.

A useful starting point

Useful to evaluate when a Rails application wants an ActiveJob-native queue with operational UI and recurring jobs. Compare its default advisory mode separately from the newer experimental SKIP LOCKED mode when planning connection pooling or upgrades.

Editorial fit, based on the cited design. Verify against your workload.

Claiming & concurrency

Documented

Default claims use session-level advisory locks. Current main documents :skiplocked, which writes lock state to the jobs table, and :hybrid for mixed rolling deployments. This snapshot evidence does not establish that those main changes are in the latest release.

Transactional enqueue

Qualified

Enqueue persists a GoodJob::Job via ActiveRecord save!. The adapter’s enqueue_after_transaction_commit setting defaults false. Sharing the application’s database connection and keeping enqueue inside its transaction can make the insert atomic; using a separate connection/database or deferred enqueue changes that boundary. This is a source-derived conditional claim.

Crash recovery & retries

Documented

Docs say interrupted jobs are automatically retried, including SIGKILL/power failure. Ordinary exceptions instead rely on ActiveJob retry_on by default. GoodJob.retry_on_unhandled_error=true enables immediate infinite retries and docs warn of high load.

Delayed & recurring work

Documented

ActiveJob delayed jobs and built-in cron are documented. Cron is opt-in (enable_cron); unique indexes suppress duplicate enqueue of a given fire interval, requiring preserved cron job records.

Uniqueness / deduplication

Qualified

GoodJob extensions offer enqueue/perform/total limits and throttles scoped by labels, plus cron-fire uniqueness. Docs warn about some state/race nuances and describe optimistic retry for perform limits. Do not equate those controls with exactly-once external effects.

Tradeoffs to carry into a test

  • Unhandled task errors are not retried by default; configure ActiveJob retry_on or explicitly choose GoodJob’s unhandled-error behavior. Interrupted processes are handled separately.

External effects still need a boundary

Because interrupted executions are retried, an external effect performed before interruption may repeat. This is an inference from documented recovery; the README’s run-once wording is not treated as a guarantee of exactly-once external effects.
