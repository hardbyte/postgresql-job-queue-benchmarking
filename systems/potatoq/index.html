What this system is built around

A Python task queue with Postgres, SQLite, Redis/Valkey and RabbitMQ transports. The Postgres transport uses short SKIP LOCKED claims and late acknowledgement, with an optional application-owned transaction for enqueue.

A useful starting point

Useful to evaluate when a Python application wants Celery-shaped task APIs, Django Tasks integration and a Postgres transport without a separate broker. The alpha status and transport-specific behavior make pinning and application-level failure tests particularly important.

Editorial fit, based on the cited design. Verify against your workload.

Claiming & concurrency

Documented

A MATERIALIZED CTE selects one job with FOR UPDATE SKIP LOCKED; the UPDATE gives the delivery a random token. Completion’s fenced DELETE matches id, running state and token before writing results/follow-ups. No transaction spans task execution.

Transactional enqueue

Qualified

For the Postgres transport, enqueue(messages, connection=...) uses the caller’s DB-API connection. Django/SQLAlchemy integrations do this for a matching database. Otherwise enqueue is deferred until commit, which retains a commit-to-publish failure window.

Crash recovery & retries

Documented

Task removal follows completion. Child-process death requeues work; a missing node is recovered after worker_dead_after (default60 s). After task_max_deliveries (default5) crashed deliveries it is dead-lettered. Task exceptions are not retried by default; retry/autoretry is opt-in.

Delayed & recurring work

Documented

ETAs/retries remain in the broker; workers promote due Postgres tasks. Every worker may schedule recurring tasks; Postgres deduplicates each (entry, fire_time) by a unique row in the same transaction as enqueue. This is schedule-fire deduplication, not generic task uniqueness.

Uniqueness / deduplication

Not built in

Arbitrary unique-task/deduplication keys and per-key concurrency limits are explicitly wishlist items. Periodic-fire deduplication is a separate implemented mechanism.

Postgres extension required

No extra documented

The Postgres broker creates regular tables and indexes itself; psycopg3 is the transport dependency. Docs require Postgres13+; Django’s minimum may be higher.

External effects still need a boundary

At-least-once delivery and claim fencing do not make an external API side effect atomic with Postgres completion. The application/provider must make repeated external operations safe. This is an inference from the documented at-least-once contract and separate result/ack transaction, not a new provider guarantee.
