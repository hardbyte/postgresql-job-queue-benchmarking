What this system is built around

The maintained original PgQ event engine, with tick-based batches.

A useful starting point

Relevant when batch event-stream consumption and existing PgQ tooling are the required contract. Deployment needs the extension and a ticker/maintenance process; verify managed-provider support.

Editorial fit, based on the cited design. Verify against your workload.

Semantics & operating model

Concise claims with their scope intact. “Not verified” means this review did not establish the answer.

Claiming & concurrency

Qualified

Work is grouped by tick windows and registered-consumer position rather than a per-job running row. Multiple-consumer/cooperative tooling belongs to the surrounding PgQ ecosystem; its full topology was not audited.

Transactional enqueue

Documented

SQL insert_event inserts into the queue within the caller transaction; snapshot/tick batches track committed event windows.

Crash recovery & retries

Qualified

An active unfinished batch is returned again by next_batch. event_retry schedules an event at an absolute or relative time. Consumers own processing and when to finish a batch.

Not verified

Uniqueness / deduplication

Not verified

No general unique-job producer API was verified. event_retry handles repeated retry insertion idempotently, which is a narrower operation.

Postgres extension required

Required

PgQ is a PostgreSQL extension with C low-level functions. pgqd is a separate maintenance/ticker daemon. Current engine README lists PostgreSQL 10–19.
