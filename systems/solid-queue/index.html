What this system is built around

A database-backed Rails ActiveJob backend supporting PostgreSQL, MySQL and SQLite. It combines short SKIP LOCKED polling with separate ready/scheduled/failed execution records and process supervision.

A useful starting point

Useful to evaluate for Rails applications seeking a framework-integrated database queue, especially when portability beyond Postgres matters. Its separate queue-database default and explicit failed-job handling need to fit the application’s transaction and recovery expectations.

Editorial fit, based on the cited design. Verify against your workload.

Claiming & concurrency

Documented

PostgreSQL9.5+ supports the SKIP LOCKED path used to avoid waiting behind other workers. Workers, dispatchers and scheduler have different roles; process heartbeats, not handler deadlines, track liveness.

Transactional enqueue

Qualified

Docs describe transactional enqueue when jobs share the application database/connection and transaction, but default configuration uses a different database. Rails enqueue_after_transaction_commit defers enqueue after commit and does not provide the same atomic handoff.

Crash recovery & retries

Qualified

Expired process heartbeats and abnormal process exits mark claimed jobs failed with ProcessPrunedError/ProcessExitError. Docs explicitly say these are not automatically retried; ActiveJob retry_on cannot catch errors recorded after the process has died. FailedExecution#retry or external automation can re-enqueue them.

Uniqueness / deduplication

Qualified

limits_concurrency uses key/group semaphores. Default conflicts block; on_conflict:discard can suppress conflicting enqueues. Duration is a release failsafe and does not establish strict execution order or universal exactly-once effects.

Tradeoffs to carry into a test

  • By default the queue uses a separate database, so application-write/queue-insert atomicity must not be assumed.

    Transaction integration ↗

  • Abrupt worker death marks in-flight work failed; automatic recovery retry is deliberately not provided. ActiveJob retry_on does not catch process-prune errors recorded by a surviving process.

External effects still need a boundary

Application SQL and a queue row can share a transaction only under the documented conditions; external network effects cannot be included in that database atomicity. Retrying a failed or interrupted operation must account for already-performed effects. This is an application-level inference, not a new delivery guarantee.
