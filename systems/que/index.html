What this system is built around

A Ruby/Postgres job queue built around session advisory locks, multithreaded workers and database transactions. Native Que jobs can put application writes and job destruction inside the same transaction.

A useful starting point

A focused choice to evaluate for Ruby applications using ActiveRecord or Sequel that want transaction control without a separate broker. Native Que jobs expose stronger database integration than the generic ActiveJob adapter.

Editorial fit, based on the cited design. Verify against your workload.

Semantics & operating model

Concise claims with their scope intact. “Not verified” means this review did not establish the answer.

Claiming & concurrency

Documented

Workers coordinate with PostgreSQL advisory locks; the worker process is multithreaded. Locking does not itself require updating the job row.

Transactional enqueue

Qualified

Enqueue can piggyback on ActiveRecord/Sequel connections and commit or roll back with application data. Native Que jobs may destroy/finish themselves in the same application transaction. Docs warn the ActiveJob adapter loses the ability to finish a job inside the same transaction as other operations.

Crash recovery & retries

Documented

Advisory locks disappear when a worker’s connection dies, making unfinished jobs available. Error retries use an increasing interval and maximum_retry_count; docs describe a default15 retries. Crash recovery can repeat a partially completed handler.

Delayed & recurring work

Qualified

Native jobs support future run_at and priority. The README lists que-scheduler as a separate cron-style project, under related projects described as tested for Que1.x; current2.x compatibility is unverified.
