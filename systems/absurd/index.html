What this system is built around

PostgreSQL durable workflows that replay task code and load persisted step results on retry.

A useful starting point

Consider for long-running processes with durable sleep, external events and checkpoint replay. Requires stable workflow code/step identities and an external strategy for recurring schedules; compare contracts before comparing throughput.

Editorial fit, based on the cited design. Verify against your workload.

Transactional enqueue

Documented

TypeScript bindToConnection runs spawn and other operations on a supplied database connection, allowing use inside an application transaction. The caller must own the transaction.

Crash recovery & retries

Documented

Workers claim a task for a bounded duration; checkpoint writes extend the claim. After expiration another worker can pick up the task; enough progress/headroom is required.

Delayed & recurring work

Qualified

Tasks can sleep or await cached named events. No built-in recurring scheduler: docs show an application scheduler or optional pg_cron plus spawn-time idempotency keys.

Uniqueness / deduplication

Documented

If a task with a matching queue-scoped idempotency key exists, spawn returns that task. Provider-side idempotency is separate.

  • This is durable workflow/checkpoint execution, not the same contract as a plain job queue or visibility-timeout message queue.

External effects still need a boundary

Retries replay completed checkpoint results. Task claims expire and can overlap briefly; a side effect before its checkpoint is persisted can still repeat, so external provider idempotency is required.
