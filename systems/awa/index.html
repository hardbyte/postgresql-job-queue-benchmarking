What this system is built around

A Rust and Python job framework using PostgreSQL for enqueue, worker claims, recovery and operational state. The inspected development revision uses segmented queue storage and claim receipts.

A useful starting point

Evaluate when Rust and Python workers need shared PostgreSQL jobs with transactional enqueue and operational controls. Test the deployed release, database settings and handler recovery behavior; the lab and old benchmark use different snapshots.

Editorial fit, based on the cited design. Verify against your workload.

Semantics & operating model

Concise claims with their scope intact. “Not verified” means this review did not establish the answer.

Claiming & concurrency

Qualified

Per-queue worker permits and an optional weighted pool govern local runtime capacity. Do not interpret global_max_workers as an automatically fleet-wide limit. Multiple claimers share one runtime’s queue permits.

Transactional enqueue

Documented

insert_with accepts the application’s PostgreSQL transaction executor. Business writes and enqueue can share one commit. The ordinary handler’s completion is separate; the ADR-042 caller-owned handler API is not implemented at this snapshot.

Crash recovery & retries

Documented

Heartbeat staleness and hard deadlines close abandoned attempts for retry/failure handling. Completion validates the open attempt identity; a rescued handler can still run late. Delivery is at least once.

Delayed & recurring work

Documented

Future run_at, retry backoff and snooze use deferred storage. A maintenance leader drives periodic/cron schedules, including timezones; a live worker fleet performs scheduling and promotion.

Uniqueness / deduplication

Qualified

Insert uniqueness is configurable by kind, queue, arguments and selected job states. It controls enqueue identity, not exactly-once handler execution or external effects.

Unique jobs ↗ Transactional enqueue and external effects ↗

Postgres extension required

Not required

Awa installs SQL schemas and migrations on PostgreSQL, without a dedicated queue extension. Worker runtimes own maintenance; pg_cron is not required for its scheduler.

Documented

The awa serve operational interface includes queues, jobs, cron and dead-letter management. Runtime and CLI versions must match the supported schema/upgrade contract.

Tradeoffs to carry into a test

  • Queue-storage claim transactions use synchronous_commit=off. A claim acknowledged before its WAL is flushed may disappear after a database crash, leaving the job claimable again.

    Claim WAL durability ↗

  • A stale-completion guard protects database state; it cannot stop an isolated old handler from calling an external service.

External effects still need a boundary

External calls cannot join the PostgreSQL enqueue/completion atomicity boundary. The documented at-least-once contract requires duplicate-safe handlers or provider idempotency.
